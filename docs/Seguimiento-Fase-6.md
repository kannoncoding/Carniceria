# Seguimiento de la fase 6

Fase 6 centraliza y prueba las transiciones de estado de factura y su efecto atomico sobre las existencias. Cada paso se completa con evidencia revisada; la interfaz de facturas corresponde a F7.

| Paso | Estado | Alcance |
| --- | --- | --- |
| F6.1 | Completado | Regla unica de transiciones en API: editar Pendiente/Pagada; pagar Pendiente; anular Pagada; eliminar Pendiente. Las combinaciones restantes y los enums no definidos devuelven conflicto 409. QA aprobo 14 casos y 26 aserciones, incluidos mensajes/campos de conflicto y ausencia de mutacion. Build de solucion: 0 errores y 0 advertencias. No implementa operaciones ni cambia existencias. |
| F6.2 | Completado | `POST /api/facturas/{numero}/pagar` acepta solo Pendiente. Bajo el mismo bloqueo agrupa la demanda, valida referencias, unidad capturada y stock actual; prepara existencias finales y copia Pagada antes de mutar. Devuelve 200 con respuesta completa, 404 si no existe y 409 ante transición inválida, stock insuficiente o unidad incompatible. No revaloriza precio ni importes. QA aprobó 86/86 verificaciones HTTP; incluye pago normal, rechazo sin mutación, líneas repetidas, unidad incompatible y pago repetido. Build de solución: 0 errores y 0 advertencias. |
| F6.3 | Completado | `PUT /api/facturas/{numero}` edita facturas Pendientes con una solicitud separada. Conserva numero, emision y estado; valida que cada Id de detalle pertenezca a la factura y no se repita. Por defecto preserva precio y unidad de lineas retenidas; `ActualizarPreciosYUnidades=true` toma ambos valores actuales de API. Las lineas nuevas o con producto sustituido usan los valores actuales. El calculo y la validacion de stock se hacen bajo el bloqueo; la operacion no modifica existencias ni secuencia. QA aprobo 150/150 verificaciones HTTP sobre Id propios, cambios opcionales, lineas nuevas o sustituidas, campos de cabecera y rechazos sin mutacion parcial. Build de solucion: 0 errores y 0 advertencias. |
| F6.4 | Completado | El mismo `PUT /api/facturas/{numero}` edita facturas Pendientes o Pagadas. Para las Pagadas agrupa lineas anteriores y nuevas y calcula cada existencia final como existencia actual mas la diferencia entre cantidades anteriores y nuevas. Valida unidades, desbordamientos y existencias antes de aplicar cualquier cambio; conserva Id, numero, emision y estado. La guarda de productos bloquea cambiar la unidad mientras haya una factura vinculada. QA aprobo 340/340 verificaciones actuales: 115 del grupo de edicion Pagada, 81 de regresion de pago y 144 de regresion de edicion Pendiente. La cobertura HTTP de la guarda incluyo facturas Pendientes y Pagadas; F6.5 verifico adicionalmente el estado Anulada. Build de API: 0 errores y 0 advertencias. |
| F6.5 | Completado | `POST /api/facturas/{numero}/anular` solo acepta facturas Pagadas. Agrupa las cantidades del detalle vigente, valida referencias, unidades y existencias, y prepara todos los reintegros antes de cambiar stock y estado. Conserva identidad, numero, emision, importes y detalles; faltante devuelve 404 y estado no permitido o repeticion devuelve 409. QA aprobo 75/75 verificaciones HTTP, incluidas ediciones previas, lineas repetidas, reintegro vigente, rechazo por overflow sin mutacion parcial y unidad de producto vinculada a factura Anulada. |
| F6.6 | Completado | `DELETE /api/facturas/{numero}` elimina solo facturas Pendientes y devuelve 204 sin cuerpo. La baja quita el registro y sus detalles embebidos sin cambiar existencias ni secuencia; Pagadas y Anuladas devuelven 409, y las ausentes 404. QA aprobo 55/55 verificaciones, incluidas consultas posteriores sin registro, numero no reutilizado, liberacion de referencias y rechazos por estado. La accion de edicion tambien devuelve 409 para una factura Anulada. |
| F6.7 | Completado | Se verificaron las guardas de bajas de cliente/empleado con facturas, producto con detalles de factura y proveedor con productos; el cambio de unidad de producto vinculado tambien se rechaza en los estados Pendiente, Pagada y Anulada. Las bajas libres se completan. QA aprobo 174/174 verificaciones, incluidas 12 carreras acotadas; en las 12 se observo la baja primero y el alta o edicion relacionada fue rechazada, sin referencias huerfanas ni cambios parciales. Es una muestra, no una demostracion formal de ambos ordenes. No se requirio cambio de API; se conserva la build valida de F6.6. |
| F6.8 | Pendiente | Preparar todos los cambios y rechazos antes de mutar factura, detalles o stock. |
| F6.9 | Pendiente | Comprobar repeticiones, concurrencia y edicion sin cambios sin efectos parciales. |

## Decisiones y limites

- F6.1 se puede implementar sin resolver el historico de precios/unidades ni el cambio de unidad de productos facturados.
- La politica de F6.1 vive en API y no acepta un estado destino arbitrario. Los endpoints y operaciones de pago, edicion y anulacion se incorporan en sus pasos posteriores.
- El pago conserva el precio, unidad e importes registrados; una unidad actual distinta causa 409 sin convertir. Esta salvaguarda no define si se permite cambiar la unidad global de un producto con facturas.
- Para futuras ediciones, se eligio conservar por defecto los precios/unidades capturados. La solicitud de edicion tendra la opcion `ActualizarPreciosYUnidades`, falsa por defecto; al activarla, las lineas existentes toman ambos valores actuales de API. La casilla visible se implementara en F7.
- La ejecucion historica de F6.3 rechazaba la edicion de facturas Pagadas con 409; F6.4 habilita esa operacion con ajuste atomico de existencias. La edicion rechaza con 409 si una unidad capturada no coincide con la unidad actual del producto, sin convertir ni mutar.
- Comentarios de codigo nuevos usan espanol sin tildes; los textos visibles conservan su ortografia normal.
- Se acordo bloquear el cambio de unidad de un producto mientras tenga facturas vinculadas, en cualquier estado. F6.4 implementa la guarda global; F6.5 verifico tambien el caso Anulada. Se conservan las salvaguardas locales de pago, edicion y anulacion.
